# Architecture



## Order Producer

The producer is written in Python and reads order and order-item data from CSV files.

Each `order_id + product_id` combination becomes an order event and is sent directly to the Bronze table through Databricks Zerobus.

The producer supports both finite and continuous execution.

### Finite Mode

Send a fixed number of events and stop:

```bash
uv run --env-file .env python src/producer/order_event_producer.py   --num-events 250
```



### Continuous Mode

Keep sending events until the process is stopped manually:

```bash
uv run --env-file .env python src/producer/order_event_producer.py   --continuous
```

Stop it with `Ctrl+C`.

The Zerobus stream is closed before the producer exits.

### Example Event

```json
{
  "order_id": "example-order-id",
  "customer_id": "example-customer-id",
  "product_id": "example-product-id",
  "quantity": 1,
  "price": 120.50,
  "order_timestamp": "2018-08-15T10:30:00+00:00",
  "discount_code": "WELCOME10",
  "ingest_datetime": "2026-08-24T09:30:00+00:00"
}
```

`order_timestamp` comes from the source order.

`ingest_datetime` is generated when the event is sent to Databricks.

# Medallion Architecture



## Bronze

Bronze receives raw order events through Databricks Zerobus.

Development table: `dbr_dev.ecommerce_bronze.brz_orders`

Customer and product source data also enters through Bronze.

Bronze preserves the original ingested data before business transformations and downstream quality routing are applied.

---



## Silver

Silver contains cleaned and validated data.

Main Silver tables: `slv_customers, slv_products, slv_product_categories, slv_orders, quarantine_orders`

`slv_customers` and `slv_products` clean and validate their source fields and keep historical changes using SCD logic.

`slv_product_categories` contains the translated product category names.

The orders flow applies explicit quality rules before records are used downstream.

### Order Quality Rules

```sql
order_id IS NOT NULL AND customer_id IS NOT NULL AND product_id IS NOT NULL AND quantity IS NOT NULL AND quantity > 0 AND price IS NOT NULL AND price >= 0
```

Valid records continue to `slv_orders`.

Invalid order records are preserved in `quarantine_orders`.

Orders are deduplicated using `order_id + product_id`.

---



## Quarantine

Rejected order events are preserved instead of silently disappearing from the pipeline.

Examples:

```text
quantity = 0 → quarantine_reason: "quantity must be greater than 0"
price = -10 → quarantine_reason: "price must be greater than or equal to 0"
customer_id = null → quarantine_reason: "customer_id is null"
```

This provides traceability for rejected records and makes the quality-routing behavior observable.

---



## Gold

Gold contains the star schema used for analytics.

Main tables: `fact_orders, dim_date, dim_customer, dim_product`

`fact_orders` is the central fact table.

```text
                 dim_date
                    │
                    │
dim_customer ─── fact_orders ─── dim_product
```

The core transformation logic is kept separate from the Lakeflow resource definitions where practical so that transformation behavior can be tested independently with pytest.

# DQX Checks

**Databricks Labs DQX** provides an independent data-quality validation layer.

The project keeps Lakeflow and DQX responsibilities separate:

```text
Lakeflow
→ applies transformations
→ routes valid records
→ routes invalid records to quarantine

DQX
→ independently checks data quality
→ reports errors and warnings
→ acts as a CI/CD quality gate
```

DQX rules are stored in:

```text
src/data_quality/checks/
├── bronze_orders.yml
├── silver_orders.yml
└── fact_orders.yml
```

The runner is `src/data_quality/run_dqx.py`.

## DQX Failure Behavior

The DQX runner reports: `Rows checked, Rows with errors, Rows with warnings`

Warnings are reported but do not fail the execution.

Errors cause the runner to raise an exception:

```text
DQX error
    │
    ▼
non-zero exit code
    │
    ▼
Azure DevOps step fails
```

This makes DQX an automated data-quality gate in CI/CD.

# Reconciliation

DQX validates data quality **within a table**.

Reconciliation validates data consistency **between layers**.

```text
DQX
→ Are the records in this table valid?

Reconciliation
→ Did the expected data arrive correctly in the next layer?
```

Reconciliation queries are stored in:

```text
src/data_quality/reconciliation/
├── bronze_to_silver.sql
└── silver_to_gold.sql
```

The runner is `src/data_quality/run_reconciliation.py`.

---



## Bronze → Silver Reconciliation

The first reconciliation compares Bronze with Silver and Quarantine.

It checks: `Bronze total records, Valid Bronze records, Invalid Bronze records, Expected Silver records, Actual Silver records, Actual Quarantine records`

The expected relationship is:

```text
Bronze
   │
   ├── Valid ───────► Silver
   │
   └── Invalid ─────► Quarantine
```

Run it with:

```bash
UV_PROJECT_ENVIRONMENT=.venv-integration uv run --env-file .env --group integration-tests --frozen python src/data_quality/run_reconciliation.py   --query bronze_to_silver.sql
```

The check returns `reconciliation_status: PASS` when expected and actual results match.

---



## Silver → Gold Reconciliation

The second reconciliation compares Silver orders with the Gold fact table.

It validates: `row count, total quantity, total amount`

Conceptually:

```text
Silver                   Gold
------------------------------------------------
COUNT(*)              =   COUNT(*)
SUM(quantity)         =   SUM(quantity)
SUM(price)            =   SUM(line_amount)
```

Run it with:

```bash
UV_PROJECT_ENVIRONMENT=.venv-integration uv run --env-file .env --group integration-tests --frozen python src/data_quality/run_reconciliation.py   --query silver_to_gold.sql
```

If any comparison fails, `reconciliation_status: FAIL` and the runner raises an exception.

This causes the corresponding Azure DevOps step to fail.

---



## Why Reconciliation Is Needed

A table can contain only valid records while still being incomplete.

For example: `Silver expected: 343, Silver actual: 340`

The 340 existing records may all pass DQX, but three expected records are missing.

Reconciliation detects this type of cross-layer consistency problem.

The distinction is therefore:

> **DQX validates data quality within a layer, while reconciliation validates completeness and consistency between layers.**

# Data Quality Alert

The Databricks data-quality alert is stored in `resources/alerts/order_data_quality.yml`.

It monitors `quarantine_orders` for recently rejected records.

Trigger condition: `invalid_records > 0`

The alert is managed through the Databricks Asset Bundle.

This provides operational visibility when invalid order events reach quarantine.

# Row Level Security

Governance SQL is stored under `src/governance/`.

Access to Gold is restricted at two levels.

## Row Level Security

A secure view filters `fact_orders` according to account group membership.

Restricted users should access the secured view rather than unrestricted underlying data.

## Column Level Security

Sensitive columns on Gold dimensions, such as `customer_unique_id`, can be masked for principals outside the authorized group.

The security layer is kept separate from Lakeflow transformation logic.

This keeps `Data Processing` separate from `Data Access Control`.

```text
      │

      │
```

```text
      │

      │
      ▼
Silver → Gold Reconciliation
      │
      ▼

```

The Lakeflow pipeline is executed after deployment using the Databricks Asset Bundle resource.

This ensures that integration tests, DQX and reconciliation checks run against freshly processed pipeline data rather than stale tables.

### Failure Behavior

```text
Unit Tests fail
→ deployment does not start

Bundle validation/deployment fails
→ Lakeflow does not run

Lakeflow fails
→ validation stage does not start

Integration Tests fail
→ DEV validation fails

DQX error occurs
→ DEV validation fails

Reconciliation returns FAIL
→ DEV validation fails
```

This creates multiple quality gates before the development deployment is considered validated.

```bash
uv run --env-file .env python src/producer/order_event_producer.py
```

Verify that `ZEROBUS_SERVER_ENDPOINT` exists in `.env`.

## Continuous Mode Reuses Orders

Continuous mode uses the complete source event pool.

When it reaches the end, it reshuffles the events and starts another cycle.

This means the same `order_id + product_id` can appear again during long runs.

Silver handles duplicates using the order and product key.

---



## Requested Number of Events Is Too Large

If `--num-events` is greater than the available source event pool, the producer stops with an error instead of silently generating unsupported events.

## Databricks Connect Authentication

Integration tests, DQX and reconciliation require valid Databricks OAuth M2M credentials.

Local execution reads them from `.env`.

Azure DevOps provides them through secure variables: `DATABRICKS_HOST, DATABRICKS_CLIENT_ID, DATABRICKS_CLIENT_SECRET, DATABRICKS_AUTH_TYPE, DATABRICKS_SERVERLESS_COMPUTE_ID`

Typical authentication mode: `oauth-m2m`

---



## Public DBFS Root Disabled

A Databricks Connect connectivity test may fail if it attempts to access `dbutils.fs.ls("/")` while Public DBFS root access is disabled.

This does not necessarily mean OAuth authentication failed.

A simple serverless Spark query can be used to validate the Databricks Connect session instead.

## PySpark and Databricks Connect Conflict

Local PySpark and Databricks Connect should not be installed into the same active virtual environment.

The project therefore uses:

```text
.venv
→ local PySpark unit tests
```

and:

```text
.venv-integration
→ Databricks Connect
→ integration tests
→ DQX
→ reconciliation
```

Use `UV_PROJECT_ENVIRONMENT=.venv-integration` for Databricks-connected validation commands.

## Stale Gold Data

If Silver contains records that are missing from Gold, verify that the Lakeflow pipeline has been executed after the latest ingestion.

The CI/CD workflow avoids this issue by running:

```text
bundle deploy
      │
      ▼
bundle run
      │
      ▼
Integration Tests
      │
      ▼
DQX
      │
      ▼
Reconciliation
```

This ensures downstream checks are executed against refreshed pipeline results.

# Security

Do not store credentials directly in Python, SQL or YAML source code.

Do not commit: `.env, client secrets, access tokens, service-principal secrets`

Development and production credentials should be stored as secure Azure DevOps variables.

The Zerobus and deployment Service Principals should receive only the permissions required for their responsibilities.

Environment-specific credentials must remain isolated between `DEV, PROD`.

Local IDE files such as `.vscode/settings.json` should not be included in project commits unless they are intentionally shared project configuration.

# Databricks Resources

The Databricks Asset Bundle manages the Databricks resources required by the project.

The repository contains resource definitions under:

```text
resources/
├── alerts/
├── jobs/
├── pipelines/
├── schemas/
└── volumes/
```

Managed resources include: `Lakeflow Declarative Pipeline, Bronze setup resources, Unity Catalog schemas, Volumes, SQL / data-quality alert, Development configuration, Production configuration`

The main Lakeflow pipeline resource is deployed and executed through the Asset Bundle during CI/CD.

Conceptually:

```text
Source Code
     │
     ▼
Databricks Asset Bundle
     │
     ├── DEV
     │
     └── PROD
     │
     ▼
Azure Databricks Resources
```

This keeps infrastructure, pipeline definitions, deployment configuration and source code versioned together.

# Testing and Data Quality Strategy

The project uses several complementary validation mechanisms.


| Validation             | Purpose                                               |
| ---------------------- | ----------------------------------------------------- |
| Unit Tests             | Validate transformation functions locally             |
| Integration Tests      | Validate behavior against deployed Databricks tables  |
| Lakeflow Quality Rules | Route valid and invalid records during processing     |
| DQX                    | Independently validate data quality within each layer |
| Reconciliation         | Validate completeness and consistency between layers  |
| Data Quality Alert     | Provide operational visibility into rejected records  |


Together they provide coverage from individual transformation logic through end-to-end data integrity.

```text
Source Data
    │
    ▼
Unit-tested transformations
    │
    ▼
Bronze
    │
    ├── DQX
    │
    ▼
Lakeflow Quality Rules
    │
    ├── Invalid ─────► Quarantine
    │
    └── Valid
            │
            ▼
          Silver
            │
            ├── DQX
            │
            ├── Bronze → Silver Reconciliation
            │
            ▼
           Gold
            │
            ├── DQX
            │
            ├── Silver → Gold Reconciliation
            │
            ▼
        Databricks SQL
            │
            ▼
          Power BI
```

This design helps ensure that the pipeline is not only successfully deployed, but that the data flowing through it remains valid, complete and consistent.
