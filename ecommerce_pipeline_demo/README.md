# Ecommerce Data Pipeline

An end-to-end ecommerce data engineering project built with **Databricks**, **Lakeflow Declarative Pipelines**, **Databricks Zerobus**, **Azure DevOps**, and **Power BI**.

The project simulates a modern ecommerce platform: order events are generated by a Python producer, ingested directly into Databricks, transformed through a Medallion Architecture, deployed through CI/CD, and consumed by an analytics layer.

<a id="overview"></a>

## Overview

The solution simulates an ecommerce platform producing order events continuously or in controlled batches. Events are generated from source ecommerce datasets and ingested into Databricks using **Zerobus**. From there, Lakeflow Declarative Pipelines process the data through Bronze, Silver, and Gold layers before the final analytical model is consumed from Power BI.

```text
CSV Source Data
      │
      ▼
Python Order Producer
      │
      ▼
Databricks Zerobus
      │
      ▼
Bronze Layer → Silver Layer → Gold Layer
      │
      ▼
Databricks SQL
      │
      ▼
Power BI
```

**Key capabilities demonstrated:**

- Event-driven data ingestion with Databricks Zerobus
- Lakeflow Declarative Pipelines
- Medallion Architecture on Delta Lake with Unity Catalog
- Data quality, transformation, and dimensional modeling
- Databricks Asset Bundles
- CI/CD with Azure DevOps
- Separate development and production environments
- Power BI analytics

<a id="architecture"></a>

## Architecture

### Order Producer

The producer is implemented in Python and reads ecommerce order and order-item data from CSV files. Each valid `order_id + product_id` combination is converted into an individual ecommerce event.

The producer supports two execution modes:

**Finite mode** — send a predefined number of events and terminate automatically.

```bash
uv run python src/producer/order_event_producer.py --num-events 250
```

**Continuous mode** — send events until manually stopped.

```bash
uv run python src/producer/order_event_producer.py --continuous
```

Continuous mode can be stopped safely with `Ctrl+C`. The producer closes the Zerobus stream cleanly before terminating.

### Example Event

```json
{
  "order_id": "example-order-id",
  "customer_id": "example-customer-id",
  "product_id": "example-product-id",
  "quantity": 1,
  "price": 120.50,
  "order_timestamp": "2018-08-15T10:30:00+00:00",
  "discount_code": "WELCOME10",
  "ingest_datetime": "2026-08-24T09:30:00+00:00"
}
```

Two timestamps are intentionally different:

| Field | Meaning |
|---|---|
| `order_timestamp` | When the source ecommerce order originally occurred |
| `ingest_datetime` | When the producer sent the event to Databricks |

<a id="medallion-architecture"></a>

## Medallion Architecture

### Bronze

Receives the raw events ingested through Zerobus. Its primary responsibility is to preserve incoming data before any downstream transformation.

```text
dbr_dev.ecommerce_bronze.brz_orders
```

> The actual catalog and schema depend on the deployment environment.

### Silver

Creates standardized, validated business data from Bronze:

- Schema enforcement
- Type conversion
- Data validation
- Deduplication
- Standardization
- Business-rule processing
- Preparation for downstream dimensional models

### Gold

Contains analytics-ready fact and dimension tables, optimized for reporting and BI workloads.

```text
fact_orders
dim_date
dim_customer
dim_product
```

## Environment Variables

The producer reads its Databricks configuration from environment variables.

**Required:**

```bash
export ZEROBUS_SERVER_ENDPOINT="<zerobus-server-endpoint>"
export DATABRICKS_WORKSPACE_URL="<databricks-workspace-url>"
export DATABRICKS_CLIENT_ID="<service-principal-client-id>"
export DATABRICKS_CLIENT_SECRET="<service-principal-client-secret>"
```

**Optional:**

```bash
export ZEROBUS_TABLE_NAME="<catalog>.<schema>.<table>"
```

If `ZEROBUS_TABLE_NAME` is not set, the producer defaults to:

```text
dbr_dev.ecommerce_bronze.brz_orders
```

> Do not commit real client secrets, access tokens, passwords, or environment files containing credentials.

<a id="running-the-producer"></a>

## Running the Producer

Run from the repository root.

**Default execution** — sends 20 events using the default batch configuration:

```bash
uv run python src/producer/order_event_producer.py
```

### Finite Mode

Use `--num-events` when a known number of events should be sent.

```bash
uv run python src/producer/order_event_producer.py --num-events 250
```

Useful for controlled tests, pipeline validation, data quality testing, reproducible demos, and comparing row counts before/after ingestion.

### Continuous Mode

```bash
uv run python src/producer/order_event_producer.py --continuous
```

Runs until manually interrupted with `Ctrl+C`. Useful for demonstrating a live event stream while observing the downstream pipeline.

When the producer reaches the end of the source event pool, it reshuffles the events and begins a new cycle.

> Continuous mode reuses source `order_id + product_id` combinations once the pool is exhausted. It does not currently generate new synthetic order IDs — plan downstream deduplication accordingly for long-running demos.

`--num-events` and `--continuous` are mutually exclusive; supplying both is rejected by the CLI.

### Batch Size

Simulates variable traffic by randomly selecting how many records go into each batch.

```bash
uv run python src/producer/order_event_producer.py \
  --num-events 250 \
  --min-batch-size 1 \
  --max-batch-size 8
```

### Batch Delay

Introduces a random delay between batches to mimic irregular application traffic.

```bash
uv run python src/producer/order_event_producer.py \
  --num-events 250 \
  --min-batch-delay 0.3 \
  --max-batch-delay 2.5
```

### Discount Codes

```bash
uv run python src/producer/order_event_producer.py \
  --num-events 250 \
  --include-discount-code
```

Available values: `SUMMER25`, `WELCOME10`, `FLASH15`, `NULL`. If the flag is omitted, `discount_code` is sent as `null`.

### Recommended Demo Commands

**Controlled demo** (exactly 250 events):

```bash
uv run python src/producer/order_event_producer.py \
  --num-events 250 \
  --min-batch-size 1 \
  --max-batch-size 8 \
  --min-batch-delay 0.3 \
  --max-batch-delay 2.5 \
  --include-discount-code
```

**Continuous streaming demo:**

```bash
uv run python src/producer/order_event_producer.py \
  --continuous \
  --min-batch-size 1 \
  --max-batch-size 8 \
  --min-batch-delay 0.3 \
  --max-batch-delay 2.5 \
  --include-discount-code
```

<a id="cicd"></a>

## CI/CD

The project uses **Azure DevOps** to validate and deploy Databricks resources. Databricks Asset Bundles provide declarative configuration for the required resources.

Deployment to **Development** and **Production** are triggered differently:

- **Development** — deploys automatically on every push to `main`.
- **Production** — only deploys when a **Git tag matching semantic versioning (`v1.0.0`, `v1.1.0`, ...)** is created. Pushing to `main` alone never touches production.

```text
Push to main
      │
      ▼
Azure DevOps Pipeline
      │
      ├── Validate Bundle
      └── Deploy to Development
              (automatic, every push)


Git tag "v1.0.0"
      │
      ▼
Azure DevOps Pipeline
      │
      ├── Validate Bundle
      └── Deploy to Production
              (only on semver tag)
```

This keeps `main` as a continuously deployed development environment, while production releases are explicit and versioned — a tag is a deliberate decision to ship, not a side effect of merging code.

To release to production:

```bash
git tag v1.0.0
git push origin v1.0.0
```

## Power BI

Power BI consumes analytical data from the Databricks Gold layer through Databricks SQL.

```text

                    │

```

Supports metrics such as total orders, revenue, average order value, sales by date, product performance, customer activity, and discount usage.

<a id="troubleshooting"></a>

## Troubleshooting

**Missing Zerobus endpoint**

```text
RuntimeError: ZEROBUS_SERVER_ENDPOINT environment variable is required
```

Configure the required environment variables (see [Environment Variables](#environment-variables)) and restart the producer.

**Environment variables work in the terminal but not in the IDE**

Environment variables belong to the process environment in which the application is started. If running from VS Code, PyCharm, or another IDE, configure the same variables in the IDE's run configuration, or start the IDE from a terminal session where they've already been exported.

**Requested number of events exceeds the source dataset**

The producer builds events from valid `order_id + product_id` combinations found in the source files. If `--num-events` exceeds the number available, the producer terminates with an explanatory error instead of silently sending fewer events.

**Continuous mode replays existing orders**

Once the full source pool has been sent, the producer reshuffles and starts a new cycle — so long-running executions may resend the same `order_id + product_id` combinations. Account for this in downstream deduplication logic.

<a id="security"></a>

## Security

- Credentials are not stored in Python source files.
- Runtime secrets are provided through environment variables.
- Production credentials should be stored in secure Azure DevOps secret variables or an equivalent secret-management mechanism.
- Databricks authentication should use service principals where appropriate.
- Secrets, tokens, and passwords must never be committed to Git.
- Local secret files should be excluded via `.gitignore`.
